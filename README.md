# Шифр Цезаря та XOR на PARCS-Python

Лабораторна робота з курсу «Хмарні обчислення»: паралельне шифрування/розшифрування
шифром Цезаря та XOR на платформі [PARCS-Python](https://github.com/Hummer12007/parcs-python)
у Google Cloud. Це порт MPI-версії (`serial.cpp` / `parallel.cpp`): ті самі алгоритми
(зсув `(b + shift) % 256`, XOR з ключем `SecretKey123!@#` і глобальним зсувом позиції),
той самий розподіл даних між процесами (`count_i = rest / (p - i)`).

| Файл | Що це |
|---|---|
| `solver.py` | розв'язок для PARCS (послідовний і два паралельні режими) |
| `inputs/*.txt` | вхідні файли для всіх запусків |
| `cluster.sh` | створює і видаляє кластер PARCS у Compute Engine |
| `run_all.sh` | надсилає всі задачі на майстер і збирає результати |
| `report.py` | будує таблицю (прискорення, ефективність) і графіки для звіту |

Код сумісний з Python 2.7 (саме він у Docker-образі `hummer12007/parcs-node`) і з Python 3.
Перевірено на справжньому PARCS-Python (Python 2.7.18, Pyro4 4.75): майстер + 3 воркери.

## Режими

Режим задається рядком `mode=` у вхідному файлі.

- **`serial`** — послідовний алгоритм. Усе рахує майстер, воркери не використовуються.
  Майстер — така сама VM `n1-standard-1`, як і воркери, тому порівняння чесне.
- **`local`** — основний паралельний режим. Кожен воркер сам генерує свою частину тексту
  (модель «дані вже лежать на вузлах»), шифрує і розшифровує її, перевіряє результат і
  повертає лише контрольні суми. По мережі майже нічого не передається, тому прискорення
  близьке до лінійного.
- **`scatter`** — дослівний порт MPI-версії. Майстер генерує весь текст, розсилає шматки
  воркерам (як `MPI_Scatterv`), збирає зашифроване (`MPI_Gatherv`), розсилає знову для
  розшифрування і збирає ще раз. Як і в C++ версії, генерація й перевірка не входять у
  виміряний час. Тут добре видно, що для Цезаря/XOR передача даних коштує набагато більше,
  ніж самі обчислення, тому прискорення менше за 1. Це теж результат, його треба пояснити у звіті.

**Перевірка коректності.** Текст генерується блоками по 1 МБ, і кожен блок має своє зерно,
тому за будь-якої кількості воркерів дані однакові. Для кожного обсягу програма друкує
«відбитки» (md5) шифротексту Цезаря та XOR. Вони мають збігатися в `serial`, `local` і `scatter`
за будь-якої кількості воркерів. Крім того, кожен запуск перевіряє, що розшифрований текст
дорівнює вихідному (`PASSED` / `FAILED`).

## Параметри вхідного файлу

```
mode=local                              # serial | local | scatter
workers=4                               # скільки воркерів узяти (0 = усі підключені)
sizes=100000000, 500000000, 1000000000  # обсяги тексту в байтах, кожен - окремий рядок таблиці
shift=3                                 # зсув Цезаря
key=SecretKey123!@#                     # ключ XOR (рядок береться повністю, разом із '#')
seed=2026                               # зерно генератора тексту
block=1048576                           # розмір блоку, байт
repeat=1                                # повтори кожного заміру (у таблиці - найкращий і середній)
```

Параметр `workers` дає змогу один раз підняти 4 воркери і просто міняти кількість у файлі,
без перестворення VM.

## Локальна перевірка (без хмари)

```bash
python solver.py inputs/test_small.txt out.txt --workers 2
```

Воркери тут імітуються окремими процесами. Цей запуск лише перевіряє, що все працює,
для замірів у звіті він не годиться.

## Розгортання в Google Cloud (Cloud Shell)

Потрібен лише проєкт GCP з активним Free Trial. Усе робиться в **Cloud Shell**: це термінал
у браузері, де `gcloud` уже встановлений і залогінений (кнопка `>_` праворуч угорі консолі).

1. Перенесіть код у Cloud Shell: або `git clone` вашого репозиторію, або в меню Cloud Shell (⋮)
   виберіть **Upload**, завантажте `parcs-caesar-xor.zip` і виконайте `unzip parcs-caesar-xor.zip`.
2. Дізнайтеся IP свого комп'ютера, наприклад на https://ifconfig.me. Він потрібен, щоб
   відкривати веб-інтерфейс PARCS у браузері.
3. Підніміть кластер:

   ```bash
   cd parcs-caesar-xor
   gcloud config set project <PROJECT_ID>
   MY_IP=<ваш IP> bash cluster.sh up 4
   ```

`cluster.sh` вмикає Compute Engine API і відкриває порт 8080 майстра лише для Cloud Shell і
вашого IP. Потім він створює `master` і `worker1`…`worker4` (`n1-standard-1`, по 1 vCPU, щоб
заміри були чесними) і чекає, поки всі воркери підключаться. Наприкінці друкує адресу майстра.

Чому не `create-with-container` з офіційного гайду: у поточному gcloud цей спосіб позначено як
deprecated. Скрипт робить те саме напряму: VM на Container-Optimized OS, а в startup-script
`docker run` з тим самим образом `hummer12007/parcs-node` і мережею хоста.

Правило `allow-all` з офіційного гайду краще не створювати: через веб-інтерфейс PARCS можна
запустити будь-який Python-код на ваших VM. Трафік між VM усередині мережі `default` і так
дозволений правилом `default-allow-internal`.

Інші команди:

```bash
bash cluster.sh status   # VM і скільки воркерів підключено
bash cluster.sh ip       # IP майстра
bash cluster.sh allow    # оновити firewall, якщо Cloud Shell перезапустився і його IP змінився
```

Якщо створення VM падає з помилкою квоти (`Quota 'CPUS' exceeded` або `IN_USE_ADDRESSES`),
запустіть `bash cluster.sh up 3` і робіть заміри на 1–3 воркерах.

## Запуск експериментів

**Автоматично** (усі 10 задач по черзі, результати в `outputs/`):

```bash
bash run_all.sh $(bash cluster.sh ip)
pip3 install --user matplotlib   # якщо його ще немає
python3 report.py outputs/
zip -r outputs.zip outputs && cloudshell download outputs.zip   # забрати результати собі
```

`report.py` створює `outputs/summary.md` (таблиці), `outputs/results.csv` і графіки
`local_time.png`, `local_speedup.png`, `scatter_time.png`, `scatter_speedup.png`.

**Вручну** через веб-інтерфейс: Add Job, solution file — `solver.py`, input file — один з
`inputs/*.txt`. Після завершення на сторінці Jobs можна завантажити output. Потім покладіть
усі output-файли в одну папку і запустіть `python report.py <папка>`.

Що запускається:

| Вхідний файл | Навіщо |
|---|---|
| `serial.txt` | базовий час для режиму `local` (100 МБ, 500 МБ, 1 ГБ) |
| `local_w1.txt` ... `local_w4.txt` | паралельний режим на 1–4 воркерах |
| `serial_small.txt` | базовий час для режиму `scatter` (10, 50, 100 МБ) |
| `scatter_w1.txt` ... `scatter_w4.txt` | порт MPI-версії на 1–4 воркерах |

Як рахується прискорення:

- `local`: S = T(serial) / T(local), за колонкою `Time` (увесь конвеєр).
- `scatter`: S = (Caesar + XOR у serial) / T(scatter). Так само, як у таблиці MPI-версії,
  де генерація й перевірка не входили в час.
- Ефективність E = S / p · 100 %.

Орієнтовний час: послідовний прохід 1 ГБ на `n1-standard-1` займає приблизно 1–2 хв,
а весь набір задач — приблизно 10–20 хвилин. Обсяги в режимі `scatter` обмежені 100 МБ, бо
майстер тримає в пам'яті весь текст і кілька його копій (у VM 3,75 ГБ).

## Після замірів

Видаліть VM, щоб не витрачати кредит:

```bash
bash cluster.sh down
```

Якщо плануєте ще заміри, VM можна просто зупинити (`bash cluster.sh stop`, потім
`bash cluster.sh start`). Після запуску зовнішня IP майстра зміниться, а воркери
перепідключаться самі.

## Що писати у звіті

- **Ідея.** Цезар і XOR побайтово незалежні, тому текст ділиться на неперервні шматки.
  Для XOR потрібен глобальний зсув позиції в ключі: `key[(offset + i) % len(key)]`.
- **Порівняння режимів.** У `local` на кожен байт припадають десятки наносекунд обчислень
  і майже нуль передачі, тому прискорення близьке до p. У `scatter` кожен байт двічі йде
  до воркера і двічі назад, ще й через base64 і серіалізацію Pyro4. Передача повільніша за
  обчислення, тому паралельна версія повільніша за послідовну. Це класичний приклад задачі,
  обмеженої комунікаціями (низька обчислювальна інтенсивність).
- **Висновок.** Розподілені обчислення виграють, коли дані вже лежать на вузлах або коли
  обчислень на байт даних багато.
